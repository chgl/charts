# ohdsi

![Version: 0.26.0](https://img.shields.io/badge/Version-0.26.0-informational?style=flat-square) ![Type: application](https://img.shields.io/badge/Type-application-informational?style=flat-square)

[OHDSI](https://github.com/OHDSI) - Helm chart for deploying OHDSI ATLAS and WebAPI.

## TL;DR

```sh
helm install ohdsi oci://ghcr.io/chgl/charts/ohdsi --create-namespace -n ohdsi
```

## Breaking Changes

### 0.26

Updates the OHDSI WebAPI to v3 and replaces the legacy ATLAS with [ATLAS 3](https://github.com/OHDSI/Atlas3).
ATLAS 3 requires WebAPI v3, which is a major rewrite (Spring Boot 3, Spring Security, Java 21).
Existing WebAPI 2.x databases are migrated automatically by Flyway on first start, but make sure to back up the database first.

- `atlas.config.local` now has to contain the contents of a JSON `config-local.json` file instead of the `config-local.js`
  JavaScript module. If unset, a minimal config is generated. Auth providers no longer need to be listed in the
  ATLAS config as ATLAS 3 discovers them from the WebAPI's `/auth/providers` endpoint.
- `atlas.constructWebApiUrlFromIngress` was removed. ATLAS now uses the relative `/WebAPI` path by default, which is served
  by the ingress or proxied to the WebAPI service by the ATLAS container itself. Use `atlas.webApiUrl` to override it.
- The ATLAS container now listens on port 8080 using Caddy instead of nginx and runs with a read-only root filesystem.
- `webApi.auth.basic.query` was removed. WebAPI v3's database authentication requires a table called `auth_user`
  with a fixed set of columns inside `webApi.auth.basic.schema`.
  See <https://github.com/OHDSI/WebAPI/blob/master/articles/DatabaseAuth_HOWTO.md> for details.
- `webApi.auth.openid.callbackApi` and `webApi.auth.openid.redirectUrl` were removed. The default `webApi.auth.openid.callbackUI`
  changed to `<ingress>/atlas/#/oauth/callback`.
  Note that WebAPI v3 fails to start if the OIDC provider at `webApi.auth.openid.oidUrl` is not reachable.
- `webApi.cors.allowedOrigin` now sets `security.cors.allowed-origins`, which WebAPI v3 always enforces, even if `webApi.cors.enabled=false`.
  If unset, it now defaults to the ingress origin (`<scheme>://<ingress.hosts[0].host>`) whenever the ingress is enabled.
  When accessing ATLAS through any other origin, e.g. a `kubectl port-forward`, add that origin, otherwise logins fail with
  `403 Forbidden`. See [Accessing ATLAS via port-forward](#accessing-atlas-via-port-forward).
- The WebAPI now signs JWTs using a secret from `webApi.auth.jwt`. If unset, a random secret is generated.
- WebAPI v3 no longer allows anonymous users to create cohort definitions. Configure `loadCohortDefinitionsJob.auth`
  to let the job authenticate with an API key or a database authentication user.
- `webApi.cors.enabled` was removed as WebAPI v3 no longer reads it.
- `webApi.metrics.serviceMonitor` was removed. It never produced metrics and WebAPI v3 doesn't include a Prometheus registry.
- The WebAPI now runs as UID/GID `101`, matching its container image, instead of `65534`.
- `cdmInitJob` and `loadCohortDefinitionsJob` now run as Helm hooks (`post-install` and, for the cohort definitions, `post-upgrade`)
  instead of plain Jobs. The cohort definition loader skips definitions whose name already exists.
  Set `cdmInitJob.runOnUpgrade=true` to also run the CDM init job on upgrades.
- `cdmInitJob` now runs as a non-root user with a read-only root filesystem by default. Override
  `cdmInitJob.podSecurityContext` and `cdmInitJob.securityContext` if your image requires otherwise.
  The default `cdmInitJob.image` changed from `docker/whalesay` to `busybox`.
- `achilles.enabled` now defaults to `false`, since the default schemas don't exist in a fresh installation.
- The jobs and init containers now always use the cluster-internal WebAPI service URL instead of `atlas.webApiUrl`.
- ServiceAccounts are now named according to `*.serviceAccount.name` and the Achilles ServiceAccount is actually created.
- `commonAnnotations` is now a map instead of a list.
- `webApi.auth.openid.callbackUI` is required if OpenID Connect is enabled without an ingress.
- Requires Kubernetes 1.21+. The fallbacks for older Ingress and CronJob API versions were removed.
- The chart now ships a `values.schema.json`, so unknown or removed keys (e.g. `atlas.constructWebApiUrlFromIngress`)
  are rejected instead of being silently ignored.

### 0.25

Switched from Bitnami PostgreSQL to Cloud Pirates PostgreSQL chart. The integrated PostgreSQL configuration is now under `.Values.postgres`.

### 0.14

Updates all object labels to follow the Bitnami chart conventions: <https://github.com/bitnami/charts/blob/master/bitnami/common/templates/_labels.tpl>.

If you have installed a previous version and attempt to update, you will most likely receive something similar to the following message:

```console
Error: UPGRADE FAILED: cannot patch "ohdsi-atlas" with kind Deployment: Deployment.apps "ohdsi-atlas" is invalid: spec.selector:
Invalid value: v1.LabelSelector{MatchLabels:map[string]string{"app.kubernetes.io/component":"atlas", "app.kubernetes.io/instance":"ohdsi", "app.kubernetes.io/name":"ohdsi"},
MatchExpressions:[]v1.LabelSelectorRequirement(nil)}: field is immutable [...]
```

Unfortunately, the only solution is to delete and re-install the chart.
The following assumes that you have previously installed version `0.13.0`
of the chart in the `ohdsi` namespace and used the included PostgreSQL sub-chart:

```sh
$ helm ls -n ohdsi
NAME    NAMESPACE       REVISION        UPDATED                                 STATUS          CHART           APP VERSION
ohdsi   ohdsi           3               2022-04-03 22:21:13.8195241 +0200 CEST  deployed        ohdsi-0.13.0    2.10.1

# if not saved anywhere else, first retrieve the password used by the PostgreSQL sub-chart
export POSTGRES_PASSWORD=$(kubectl get secret --namespace ohdsi ohdsi-postgresql -o jsonpath="{.data.postgres-password}" | base64 --decode)

# if you depend on the data used by the PostgreSQL sub-chart, please make sure
# uninstalling the release doesn't automatically delete the PVC before running the following
$ helm uninstall -n ohdsi ohdsi
release "ohdsi" uninstalled

$ kubectl get pvc -n ohdsi
NAME                      STATUS   VOLUME                                     CAPACITY   ACCESS MODES   STORAGECLASS   AGE
data-ohdsi-postgresql-0   Bound    pvc-91614c49-cfe6-421a-8990-3317dfd88030   8Gi        RWO            standard       17m

# this uses the $POSTGRES_PASSWORD retrieved in the first step
# since we didn't rename the release, this will re-use the PVC `data-ohdsi-postgresql-0` used for the previous installation
helm upgrade --install -n ohdsi --render-subchart-notes --set postgresql.auth.postgresPassword="${POSTGRES_PASSWORD}" ohdsi charts/ohdsi/
```

### 0.12

Updates the included Bitnami PostgreSQL sub-chart to v11. The default Postgres version is now 14.2.

Steps to upgrade from an existing installation:

1. if you are using the sub-chart, either manually upgrade an existing postgres installation to v14.2 or set `postgresql.image.tag: 13.1.0`.
1. the default key name for the postgres secret has been renamed from `postgresql-password` to `postgres-password`. If you are using the `existingSecret` option, you may have to manually update accordingly.
1. if you are overriding any other of the sub-chart's values, please see <https://docs.bitnami.com/kubernetes/infrastructure/postgresql/administration/upgrade/> for instructions on upgrading.

### 0.4

Starting with v0.4.0, the two separate ingress resources for WebAPI and Atlas have been merged into a single one with the `/WebAPI/` and `/atlas/` paths
mapping to the WebAPI and Atlas service respectively. Set `ingress.enabled=true` and configure `ingress.hosts[]` to enabled it.

## Introduction

This chart deploys the OHDSI WebAPI and ATLAS app on a [Kubernetes](http://kubernetes.io) cluster using the [Helm](https://helm.sh) package manager.

## Prerequisites

- Kubernetes v1.21+
- Helm v3

## Installing the Chart

To install the chart with the release name `ohdsi`:

```sh
helm install ohdsi oci://ghcr.io/chgl/charts/ohdsi -n ohdsi
```

The command deploys the OHDSI WebAPI and ATLAS app on the Kubernetes cluster in the default configuration. The [configuration](#configuration) section lists the parameters that can be configured during installation.

> **Tip**: List all releases using `helm list`

## Uninstalling the Chart

To uninstall/delete the `ohdsi`:

```sh
helm delete ohdsi -n ohdsi
```

The command removes all the Kubernetes components associated with the chart and deletes the release.

## Initialize the CDM using a custom container

The `cdmInitJob` configuration parameter can be used to configure a custom container that is run as a Kubernetes Job
when the chart is installed (a `post-install` Helm hook). Set `cdmInitJob.runOnUpgrade=true` to also run it on every upgrade,
which requires the container to be idempotent. The job runs as a non-root user with a read-only root filesystem by default,
see `cdmInitJob.podSecurityContext` and `cdmInitJob.securityContext`. See [templates/cdm-init-job.yaml](templates/cdm-init-job.yaml) for a list of default environment
variables passed to the container.

As an example, here's one such container's `entrypoint.sh` and the associated Dockerfile below:

```sh
#!/bin/bash
set -e

OMOP_INIT_BASE_DIR="/opt/omop-init"

SOURCES_DIR="$OMOP_INIT_BASE_DIR/sources"
VOCABS_DIR="$OMOP_INIT_BASE_DIR/vocabs"
SCHEMAS_DIR="$OMOP_INIT_BASE_DIR/schemas"
POSTINIT_DIR="$OMOP_INIT_BASE_DIR/postinit"

WEBAPI_URL=${WEBAPI_URL:?"WEBAPI_URL required but not set"}
PGPASSWORD=${PGPASSWORD:?"PGPASSWORD required but not set"}
PGHOST=${PGHOST:?"PGHOST required but not set"}

export PGDATABASE=${PGDATABASE:-"ohdsi"}
export PGUSER=${PGUSER:-"postgres"}
export PGPORT=${PGPORT:-"5432"}

CDM_DIR="$VOCABS_DIR/cdm"

mkdir -p "$VOCABS_DIR"

echo "$(date): Extracting CDM vocabs"
tar -xzvf "$SOURCES_DIR/cdm.tar.gz" -C "$VOCABS_DIR/"

echo "$(date): Checking if Postgres @ $PGHOST:$PGPORT is up"
until psql -c "select 1"; do
    echo "$(date): Waiting for Postgres to be up"
    sleep 5
done
echo "$(date): Postgres is up"

echo "$(date): Creating Schema"
for SQL_FILE in init_omop/*; do
    echo "$(date): Applying $SQL_FILE"
    psql -f "$SQL_FILE"
done

echo "$(date): Copying vocabulary"

psql <<-EOSQL
    \COPY cdm.drug_strength FROM '$CDM_DIR/DRUG_STRENGTH.csv' WITH DELIMITER E'\t' CSV HEADER QUOTE E'\b';
    \COPY cdm.concept FROM '$CDM_DIR/CONCEPT.csv' WITH DELIMITER E'\t' CSV HEADER QUOTE E'\b';
    \COPY cdm.concept_relationship FROM '$CDM_DIR/CONCEPT_RELATIONSHIP.csv' WITH DELIMITER E'\t' CSV HEADER QUOTE E'\b';
    \COPY cdm.concept_ancestor FROM '$CDM_DIR/CONCEPT_ANCESTOR.csv' WITH DELIMITER E'\t' CSV HEADER QUOTE E'\b';
    \COPY cdm.concept_synonym FROM '$CDM_DIR/CONCEPT_SYNONYM.csv' WITH DELIMITER E'\t' CSV HEADER QUOTE E'\b';
    \COPY cdm.vocabulary FROM '$CDM_DIR/VOCABULARY.csv' WITH DELIMITER E'\t' CSV HEADER QUOTE E'\b';
    \COPY cdm.relationship FROM '$CDM_DIR/RELATIONSHIP.csv' WITH DELIMITER E'\t' CSV HEADER QUOTE E'\b';
    \COPY cdm.concept_class FROM '$CDM_DIR/CONCEPT_CLASS.csv' WITH DELIMITER E'\t' CSV HEADER QUOTE E'\b';
    \COPY cdm.domain FROM '$CDM_DIR/DOMAIN.csv' WITH DELIMITER E'\t' CSV HEADER QUOTE E'\b';
EOSQL

echo "$(date): Creating DB indices"
PGOPTIONS=--search_path=cdm psql -f "$POSTINIT_DIR/indexes.sql"

echo "$(date): Creating DB constraints"
PGOPTIONS=--search_path=cdm psql -f "$POSTINIT_DIR/constraints.sql"

echo "$(date): Creating CDM results tables"
PGOPTIONS=--search_path=cdm psql -f "$POSTINIT_DIR/restabs_cdm.sql"

echo "$(date): Waiting for WebAPI @ $WEBAPI_URL to be up"
until [ "$(curl -s -o /dev/null -L -w '%{http_code}' "$WEBAPI_URL/info")" == "200" ]; do
    echo "$(date): Waiting for WebAPI to be up"
    sleep 5
done

# This is better solved by invoking the WebAPI dynamically instead
echo "$(date): Updating OHDSI WebAPI CDM sources"
psql <<-EOSQL
    INSERT INTO ohdsi.source(source_id, source_name, source_key, source_connection, username, password, source_dialect)
    VALUES (1, 'CDM V5.3.1 Database', 'CDMV5', 'jdbc:postgresql://${PGHOST}:${PGPORT}/${PGDATABASE}', '$PGUSER', '$PGPASSWORD', 'postgresql');

    INSERT INTO ohdsi.source_daimon(source_daimon_id, source_id, daimon_type, table_qualifier, priority)
    VALUES (5, 1, 0, 'cdm', 2);

    INSERT INTO ohdsi.source_daimon(source_daimon_id, source_id, daimon_type, table_qualifier, priority)
    VALUES (6, 1, 1, 'cdm', 2);

    INSERT INTO ohdsi.source_daimon(source_daimon_id, source_id, daimon_type, table_qualifier, priority)
    VALUES (7, 1, 2, 'cdm_results', 2);

    INSERT INTO ohdsi.source_daimon(source_daimon_id, source_id, daimon_type, table_qualifier, priority)
    VALUES (8, 1, 3, 'cdm_results', 2);
EOSQL

echo "$(date): Refreshing sources"
curl -s -L -o /dev/null "$WEBAPI_URL/source/refresh"

echo "$(date): Completed initialization."
exit 0
```

```Dockerfile
FROM alpine:3.12
# hadolint ignore=DL3018
RUN apk --no-cache --repository=http://dl-cdn.alpinelinux.org/alpine/edge/main add \
    curl \
    bash \
    postgresql-client

WORKDIR /opt/omop-init/sources

ARG CDM_URL=https://<s3-url>/tar-gz-containing-cdm-vocabulary

    -o cdm.tar.gz

WORKDIR /opt/omop-init

# contains the CDM schema SQLs (fetching this within the Dockerfile may be cleaner)
COPY --chown=10001:10001 init_omop init_omop/
# scripts to setup custom schema names
COPY --chown=10001:10001 init_scripts init_scripts/
# scripts to apply indexes
COPY --chown=10001:10001 postinit postinit/
# the entrypoint.sh from above
COPY --chown=10001:10001 entrypoint.sh /entrypoint.sh

USER 10001
ENTRYPOINT [ "/bin/bash" ]
CMD [ "/entrypoint.sh" ]
```

## Accessing ATLAS via port-forward

The ATLAS container proxies `/WebAPI` to the WebAPI service, so a port-forward to the ATLAS service is sufficient to use it:

```sh
kubectl port-forward -n ohdsi svc/ohdsi-atlas 8080:8080
```

and open <http://localhost:8080/atlas/>.

The WebAPI v3 rejects state-changing requests like logins with `403 Forbidden` if their `Origin` isn't allowed.
If authentication is enabled, add the port-forward's origin to the allowed origins. Include the ingress origin as well
if you use one, since setting `webApi.cors.allowedOrigin` replaces the default derived from the ingress:

```yaml
webApi:
  cors:
    allowedOrigin: "https://ohdsi.example.com,http://localhost:8080"
```

## Override config-local.json for Atlas

To use a custom `config-local.json` file to configure ATLAS, you can use the `atlas.config.local` key.
See <https://github.com/OHDSI/Atlas3/blob/develop/public/config-local.example.json> for all available settings:

```yaml
atlas:
  config:
    local: |
      {
        "api": { "url": "/WebAPI" },
        "userAuthenticationEnabled": true,
        "enableSkipLogin": false,
        "enablePermissionManagement": true
      }
```

## Securing Atlas using OpenID Connect

You can secure the access to the WebAPI and consequently limit what ATLAS users can and cannot do.
ATLAS automatically shows the auth providers enabled in the WebAPI and `userAuthenticationEnabled` is set in the generated
`config-local.json` if any of the `webApi.auth` providers is enabled.

As an example, here's a values.yaml file that enables OpenID Connect authentication:

```yaml
ingress:
  enabled: true
  hosts:
    - host: omop.example.com
  tls:
    - secretName: omop.example.com-tls
      hosts:
        - omop.example.com
webApi:
  auth:
    # comma-separated logins to grant the built-in admin role at authentication
    adminLogins: "alice"
    openid:
      enabled: true
      clientId: "ohdsi"
      clientSecret: "a5f55a03-ca7d-4a52-a352-498defb2f6fa" # betterleaks:allow
      # Required. Points to the issuer or openid-configuration endpoint of the provider.
      # Note that the WebAPI fails to start if this URL is unreachable.
      oidUrl: "https://auth.example.com/realms/OHDSI/.well-known/openid-configuration"
      # URL of the ATLAS UI OAuth callback, e.g. `https://example.com/atlas/#/oauth/callback`.
      # If unset, a URL is constructed from `ingress.hosts[0]`
      callbackUI: ""
```

The WebAPI's OAuth redirect URI that needs to be registered with the provider is `https://omop.example.com/WebAPI/user/oauth/callback/openid`.
